# RAG 增强的漏洞研判：设计文档（P1）

2026-10-20 · 分支 `feat/rag-triage`

调研依据：
- `research/p1_code_rag.md`（代码安全 RAG、数据集、仓库内容注入）
- Probewise 仓库的 `research/p1_02_rag_poisoning.md`（RAG 投毒）
- Probewise 仓库的 `research/p1_03_retrieval_stack.md`（检索模型与向量库）

## 1. 要解决的问题

扫描器靠正则规则找漏洞，误报多。比如命中了 `exec(... + ...)`，但拼进去的变量其实是常量，或者已经过白名单校验。现有的「AI 研判」把代码窗口原样发给云端大模型「裸判」，存在三个问题：

1. **大模型手里没有知识。** 它不知道这条规则对应的 CWE 有哪些安全写法，也不知道真实案例里漏洞和修复分别长什么样。
2. **被扫描的仓库由攻击者控制。** 代码注释、字符串、README 里可以写「已通过安全审查」，诱导大模型把真漏洞判成误报。
3. **数据要发给云端。** 很多企业不允许这样做。

## 2. 目标与成功标准

- **主指标**：在 **真漏洞保留率 ≥ 95%** 的前提下，误报被正确排除的比例；同时报告「被错误排除的真漏洞数」，这是代价最高的错误。
- **对比顺序**（消融实验）：
  1. 不用大模型；
  2. 大模型裸判；
  3. 加规则卡片；
  4. 再加检索到的知识条目；
  5. 再加防御措施。
- **安全指标**：
  - 往真漏洞的代码里植入注入文本后，被翻成误报的比例；
  - 向知识库投毒后，被翻成误报的比例；
  - 两项都要测「加防御前」和「加防御后」。
- **全部在本地运行**：模型通过 vLLM 部署在 H100 上，不调用任何云端 API。
- **数字全部来自实际运行。** 如果没有提升，也照实写。

## 3. 架构

```
扫描器（Node）── 命中规则 ──► aiAnalysis.js（新增 provider: local-rag）
                                   │  HTTP
                                   ▼
                     rag/ 研判服务（Python, FastAPI）
   ┌───────────────────────────────────────────────────────────────┐
   │ ① 规则卡片：按 CWE 精确取（CWE 说明、缓解措施、安全写法、修复模板）  │
   │ ② 知识条目检索：BM25 + 向量（Qwen3-Embedding-0.6B, FAISS）         │
   │    → RRF 融合 → Qwen3-Reranker-0.6B 重排 → 取前 3 条              │
   │    检索链路用 LangChain 实现；另有一版手写实现作对照               │
   │ ③ 研判：本地大模型（vLLM：Qwen3-8B / Qwen2.5-7B）                  │
   │    代码加数据标记；输出严格 JSON，必须引用知识条目 id              │
   │ ④ 护栏（判定权不交给模型）：                                      │
   │    - 「误报」只有在引用了确定性检查能确认的安全写法时才成立，        │
   │      否则降为「需人工复核」，不会降为「安全」                       │
   │    - 双判：原代码一次、去掉注释和字符串后再判一次；                  │
   │      只在带注释时才判安全的 → 标记为「受注释影响」，不放行          │
   │    - 只能引用实际检索到的条目，引用不在检索集里就作废              │
   └───────────────────────────────────────────────────────────────┘
```

## 4. 知识库（只读，离线构建，带哈希清单）

| 来源 | 内容 | 许可 |
|---|---|---|
| CWE（MITRE） | 规则对应的 CWE：说明、缓解措施、正反示例代码 | MITRE 使用条款，保留版权声明 |
| OWASP Cheat Sheet Series | 命令注入防御、SQL 注入防御、路径遍历、XSS 防御等章节 | CC BY-SA 4.0，每条注明出处，知识库作为单独的数据文件存放 |
| （扩展）CVEfixes | 真实的「漏洞提交 → 修复提交」，提炼成 Vul-RAG 风格的知识条目 | 数据 CC BY 4.0 |

- **知识条目格式**：`{id, cwe, language, kind: unsafe_pattern|safe_idiom|fix, title, text, code?, source, license, sha256}`
- **永不索引被扫描的仓库，也永不索引评测集里的代码。** 有一份清单列出每个条目的 sha256，任何人都可以审计知识库里有没有混进评测数据。

## 5. 评测设计

### 数据

**OWASP Benchmark v1.2（Java）**。只取和扫描器规则对应的四类：

| 类别 | 真漏洞 | 误报 |
|---|---|---|
| 命令注入（cmdi） | 126 | 125 |
| SQL 注入（sqli） | 272 | 232 |
| 路径遍历（pathtraver） | 133 | 135 |
| XSS | 246 | 209 |
| **合计** | **777** | **701** |

- **候选告警的构造**：把每个用例都当作「扫描器报了一条该类告警」。这相当于一个误报率很高、但不漏报的 SAST，正好用来测研判能排掉多少误报。另外单独报告扫描器自身的正则规则在 Benchmark 上实际能命中多少，如实说明规则的覆盖率。
- **数据切分**：按类别和标签分层，抽 20% 作开发集，只用来调提示词和阈值；剩下 80% 作测试集，最终数字只报测试集。
- **数据污染检查**：Benchmark 是 2016 年就公开的数据集，模型很可能见过答案。因此另做一份**混淆版**：改掉类名和测试编号、去掉注释、改掉请求头名称。两版都报告，如果差距明显，说明模型在「背答案」。

### 检索质量

人工标注 50 个查询，计算 Recall@k，比较四种检索方式：BM25、纯向量、混合检索、混合检索加重排。另外，下游研判准确率也作为检索方式的比较指标。

### 攻击实验（只在测试集的真漏洞用例上做）

| 威胁 | 做法 | 指标 |
|---|---|---|
| 仓库内容注入 | 在真漏洞代码里加入「已通过安全审查」类注释、字符串、伪造的「安全」函数名；对照组加入等长的无害注释 | 真漏洞被翻成误报的比例 |
| 自适应攻击 | 攻击者已知防御方式，针对性改写注入文本，最多迭代 N 轮 | 同上 |
| 知识库投毒 | 往知识库里混入伪造的「这种写法是安全的」条目，并且针对目标 sink 做过优化 | 同上，以及投毒条目被检索到的比例 |

## 6. 不做的事

- 不对第三方仓库做真实的漏洞利用；评测只用公开的标注数据集。
- 自动修复补丁放到扩展项：生成补丁后重新跑规则，确认告警消失且没有产生新告警；用 Juice Shop 的 codefixes 数据评测。
- 线上演示服务器没有 GPU，所以演示展示的是已经跑好的研判记录和评测结果，页面上会注明。

## 7. 风险

- 调研显示，7–8B 本地模型做漏洞判断的提升可能很有限（Vul-RAG 的复现实验在约 0.30 处遇到瓶颈）。真遇到这种情况就照实报告，并说明护栏单独起了多大作用。
- Benchmark 是 Java 用例，而扫描器的规则偏 JS / Python。所以「研判能力」和「规则覆盖」分开报告，不混在一起。

## 8. 红队评审后的修改（2026-10-20，见 research/p1_redteam.md）

| 评审意见 | 修改 |
|---|---|
| 「安全写法检查器」覆盖不了 Benchmark 的误报（多为死分支、变量被覆盖、取错 Map 键这类控制流原因），导致大模型实际上没有作用；而且去掉字符串会丢掉判断依据 | 改为**「类型化理由 + 确定性核验器」**：大模型必须给出机器能检查的理由，取值为 `dead_branch` / `overwritten` / `key_mismatch` / `sanitizer` / `param_query`，同时给出行号和表达式。核验器（Java 语法树分析）检查三件事：引用必须出自代码本身，不能出自注释或字符串；理由必须成立（常量折叠、变量定义和使用分析）；净化函数必须来自外部库，不能定义在被扫描的仓库里。三项都通过才排除这条告警，否则交给人工复核。只去掉注释，不再去掉字符串 |
| 知识检索解决不了控制流问题 | 增加**「代码上下文」**实验组：检索被扫描仓库里被调用函数的函数体，这部分作为不可信数据单独存放；再增加**等长随机知识**对照组，排除「只是提示词变长了」的解释。实验组为：裸判 / 加规则卡片 / 加代码上下文 / 加知识检索 / 加随机知识 / 加核验器 |
| 「每个用例算一条告警」反映不了扫描器的真实能力；Java 的 sink 规则几乎全部不命中；CWE-78 规则里 `\+\b` 有 bug | 补充 Java sink 规则，修复这个 bug，如实报告扫描器在 Benchmark 上的真实命中率；评测定位为「研判组件评测」，不与 ZeroFalse 的 F1 直接比较 |
| 数据污染检查太弱；随机切分会让同一种代码模板同时出现在开发集和测试集 | 混淆时同时改掉 URL 中的类别名、辅助类的包名和函数名；增加**反事实翻转对**（只做最小修改把标签翻转，约 100 对），检查模型是在「看懂代码」还是在「认模板」；按代码模板分组切分；提示词定版后冻结，每次修改都记录 |
| 三分类下指标没说清楚，统计不够严谨 | 「复核」不算作排除；阈值只在开发集上定；测试集报告真漏洞保留率的自助法置信区间；各实验组之间做配对检验；差异小于约 5 个百分点视为「测不出」 |
| 攻击实验的参数不具体 | 只在原本判对的 100 个真漏洞上测；注释、字符串、标识符三种注入位置分开测；自适应攻击者每个目标迭代 10 轮；知识库投毒定位为「纵深防御」，即「就算知识库被完全攻破，核验器也能把攻击成功率压到多少」 |
| 范围 | 去掉：LangChain 与手写版的对照（只保留 LangChain）、Recall@k 人工标注、重排和融合的消融实验、CVEfixes、Qwen2.5-7B 的大部分实验组；大模型用 FP8 量化 |

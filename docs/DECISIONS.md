# 关键决策和理由（供面试复盘）

每条记录四项：当时面临什么选择、选了哪个、为什么，以及没选的方案为什么不选。

## D1　RAG 做在扫描器上，而不是 Probewise（2026-10-20，用户选定）
- **选择**：在扫描器上做 RAG，用来研判漏洞和给出修复建议。
- **为什么**：
  - RAG 最擅长「带出处地解释和给建议」，这正是扫描器缺的；
  - 被扫描的仓库由攻击者控制，注入威胁真实存在；
  - 两个项目各有亮点，作品集更均衡。
- **没选**：Probewise 的「相似工单检索」。它和已有的「规则历史」检查高度重合，查到的相似告警大多属于同一条规则，很可能测不出提升。

## D2　评测用 OWASP Benchmark，而不是自己造数据
- **选择**：OWASP Benchmark v1.2，只取 cmdi / sqli / pathtraver / xss 四类，共 1,478 个用例。
- **为什么**：
  - 它是业界标准，每个用例都标好了「真漏洞 / 误报」；
  - 论文 ZeroFalse 也在这个数据集上报告过结果，可以对照；
  - 许可证 GPL-2.0，只在本地评测，不再分发。
- **没选**：
  - CVEfixes / PrimeVul：标签是「函数有没有漏洞」，不是「这条 SAST 告警是不是误报」，和我们的任务不一致；
  - 自己造数据：别人没法复现，面试也站不住。
- **已知问题**：它是 Java 用例，而且 2016 年就公开了，模型可能见过答案。所以另做一份混淆版来检查。

## D3　判定权不交给大模型
- **选择**：大模型判「误报」时，必须引用一个能被确定性检查确认的安全写法，否则只能降为「需人工复核」。
- **为什么**：
  - 调研显示，自适应攻击者可以用注释骗过大模型漏洞检测器，成功率超过 90%（ALIBI, 2026）；
  - 用静态分析交叉验证，是实测效果最好的防御（Thornton, 2026）；
  - 这和 Probewise「模型只负责读，判定交给可审计机制」的思路一致。
- **没选**：只靠提示词加固。论文显示效果有限。

## D4　向量库用 FAISS 精确检索，不用 Milvus / Qdrant
- **为什么**：知识库只有几千条，精确检索几毫秒就能完成，不需要分布式数据库，部署也最简单。检索器放在一个小接口后面，以后要换 Qdrant 只需要改一处。
- **没选**：
  - Milvus Lite：官方文档写明不支持 Windows；
  - Milvus 集群：对这么小的数据量是过度设计。

## D5　检索链路用 LangChain，另外手写一版作对照
- **为什么**：LangChain 在 JD 里的提及率是 21%，这次在真实项目里用一遍。同时手写一版做对照，能讲清楚框架实际帮了什么、带来了什么限制。

## D6　Embedding 用 Qwen3-Embedding-0.6B，重排用 Qwen3-Reranker-0.6B
- **为什么**：
  - 两个模型在代码检索的公开评测上都优于 bge 系列（Qwen3-Embedding 的 MTEB-Code 为 75.4，bge-m3 为 58.2，均为厂商自报）；
  - 许可证都是 Apache-2.0；
  - 体积小，可以和大模型放在同一张 H100 上。
- **没选**：
  - jina 系列：许可证不允许商用；
  - bge-reranker-v2-m3：代码重排得分只有 41。

## D7　判定护栏改成「类型化理由 + 确定性核验」（红队评审后修改）
- **选择**：大模型判误报时，必须给出机器能检查的理由，比如「第 52 行的分支永远不会执行，因为 (7*42)-86 > 200 恒为假」，由语法树分析程序核对，核对通过才算数。
- **为什么**：最初的方案是检查「安全写法」，比如参数化查询。但 Benchmark 里大多数误报是控制流造成的（死分支、变量被覆盖、取错 Map 键），这个检查器一条都确认不了。结果要么是大模型没有用武之地，要么是只能放任大模型自己说了算。
- **好处**：大模型负责「找理由」，核验器负责「确认理由」。注释里写什么都改变不了核验结果，所以注入攻击最多只能让告警进入人工复核，不能让它被直接排除。

## D8　把「检索代码上下文」也算作 RAG 的一部分，和「检索知识」分开测
- **为什么**：判断一条告警是不是误报，往往需要看被调用的函数里做了什么，这是「检索被扫描仓库的代码」。CWE 规范文本补不上这块信息。两者分开测，才能说清楚到底是哪一部分起了作用。
- **安全上的区别**：知识库是可信的，离线构建、只读；代码上下文来自被扫描的仓库，是不可信的，放在单独的数据区，只当作数据。

## D9　模型不再「下结论」，只负责「指出可能的误报原因在哪一行」
- **背景**：v1 让模型给出结论和一个理由。结果是非思考模式下，模型大多直接判「真漏洞」；即使判误报，理由也大多核验不通过。
- **改为**（v2）：模型最多提出 3 个候选理由，核验器以「模型指出的行和原文」为准，自己判断这一行属于哪种理由（死分支 / 集合取值 / 编码函数等）。
- **为什么安全**：核验器自检时，在全部 777 个真漏洞用例上，把每一行、每种理由类型都试过，没有一个能通过。所以无论模型指向哪一行，都不可能放走真漏洞。
- **效果**（开发集，思考模式）：误报排除率从「只用程序分析」的 17.9% 提升到 62.1%，真漏洞被误排除为 0。

## D10　最终方案不用知识检索（RAG 负结果）
- **数据**（开发集，思考模式，核验后）：裸判 62.1%，知识检索 57.9%，随机知识 61.4%，置信区间全部重叠。不加核验时，知识检索让模型错放的真漏洞从 4 条增加到 9 条。
- **解读**：这类告警判断难在「推理代码会不会执行到那里」，而不是缺少安全知识。往提示词里加知识只会让模型更敢判误报，不会更准。这和 Vul-RAG 复现实验的结论一致：在小模型上，知识带来的提升很有限。
- **保留**：知识库和检索链路保留在代码里，供「修复建议」使用，因为修复建议需要引用 OWASP / CWE 的出处。但它不参与误报判定。

## D11　评测全部用混淆版代码
- **数据**：同一个模型、同一批开发集，原版代码的误报排除率是 47.9%，混淆版只有 19.3%。原版里 `"safe"`、`"This_should_always_happen"`、`getInsecureOSCommandString` 这类字样会直接暗示答案。
- **决定**：所有正式数字都用混淆版；原版的数字只作为「数据污染有多严重」的证据。

## D12　核验器重写为「看不懂就拒绝」（代码审查发现 v1 只在 Benchmark 上安全）
- **问题**：代码审查手写了 25 个真实漏洞，v1 核验器把其中 23 个误判为安全，其中 18 个连大模型都没用，光程序分析就放行了。v1 的「保守分析」只覆盖了 Benchmark 里出现的写法：
  - 链式调用 `sb.append(..).append(用户输入)`；
  - 数组 / 对象字段 / `this.f`；
  - 别名 `List b = a`；
  - 请求参数不叫 `request`；
  - catch 块、没有 default 的 switch、条件表达式里的赋值、try-with-resources、`synchronized`、for 初始化语句；
  - lambda；
  - 不认识的危险函数（如 `Files.readString`）；
  - 白名单用后缀匹配（`unescapeHtml` 也能通过）；
  - 常量折叠没按 Java 语义（`-7/2`、`n++`、字符串 `==`、键名 `"k"`）。
- **改为**（v2）：遇到看不懂的写法一律拒绝核验、交给人工：
  - 任何地方引用了被污染的值就算污染；
  - 被污染的值传进方法，接收者和作为参数的对象都算污染；
  - 字段只要在任何地方被赋过非字面量就算污染；
  - 别名一起污染；
  - 控制流按「任意一点」合并；
  - lambda、匿名类、重载、不认识的语句、像危险调用但不认识的写法 → 拒绝；
  - 白名单按完整名字精确匹配并检查参数个数；
  - 常量折叠按 Java 整数语义计算；
  - 扫描器报警的每一行都必须是核验器认识并检查过的危险函数。
- **验证**：25 个反例全部保留，作为回归测试 `rag/test_verifier_probe.py`；Benchmark 自检中真漏洞上仍然没有任何理由能通过；测试集误报排除率 56.0% → 56.7%，因为 v2 认识的危险函数更多了，之前「找不到危险函数」的用例现在能分析了。
- **教训**：v1 是对着 Benchmark 写的，自检也只在 Benchmark 上做，所以「0 个真漏洞被误排除」只说明了它在 Benchmark 上安全。安全组件必须用独立构造的反例去测，不能只用开发它时看到的数据。
